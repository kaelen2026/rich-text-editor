# 性能基准与 CI 门禁

运行 `pnpm bench` 会构造固定负载：5 万个 Unicode 字符、300 个顶层段落、50 张图片、20 个 3×3 表格和 4 层列表。输出以下六项指标：

- 编辑器完成装载并可供订阅的耗时。
- 选区格式化后的状态更新 p95。
- 解析 1 万字外部 HTML 粘贴的耗时。
- 工具栏状态计算耗时。
- 字数统计耗时（内容变更后的第一次读取）。
- 装载、读取 JSON 和渲染 HTML 的堆内存增量。

GitHub Actions 的 `Quality` 检查会运行该命令，任何指标超过上限都会失败并显示具体指标。

基准通过 jsdom 挂载 `EditorView`，因此可覆盖装载、事务和 DOM 更新路径，但不代表真实浏览器的布局、绘制或 GPU 性能。

## 当前阈值还没有校准

`scripts/benchmark.ts` 里的 `PERFORMANCE_BASELINES` 是**立项时拍出来的初始值**，不是采集来的 CI 历史基线；上限由基线加 20% 余量算出。

这件事的后果要说清楚：本地一次实测下来，多数指标只有当前上限的 **1/30 到 1/90**（例如挂载 35ms 对 1200ms、工具栏 2.6ms 对 96ms）。也就是说，**今天即使出现十倍的性能回归，这道门禁也不会响**。它现在拦的是"彻底跑崩"，不是"变慢了"。

校准前它仍然值得留着——崩溃级回归也是回归——但别把它当成性能有人看着的证据。

## 怎么校准

阈值要能代表 CI 那台机器的真实分布，因此需要真实的连续运行记录，编不出来。流程：

1. **攒样本。** 每次 `Quality` 运行都会把 `bench-run.json` 归档成 artifact（`bench-<run>-<attempt>`，保留 90 天），里面是这一次的六项测量值加上环境信息（Node 版本、平台、runner 名）。攒够**同环境至少三次**。
2. **反推基线。** 下载那几个 artifact，运行：

   ```sh
   node scripts/calibrate-budgets.mjs bench-run-1.json bench-run-2.json bench-run-3.json
   ```

   它按环境分组，样本不足三次的组直接跳过，并打印可直接替换的 `PERFORMANCE_BASELINES`。
3. **在同一个 PR 里**更新 `scripts/benchmark.ts` 的常量和本文件，并把采样的运行链接与日期写下来——让下一个人知道这组数字是哪来的。

### 三条取样口径

- **按环境分组。** 本机和 CI runner 的结果不可比。混在一起算出的阈值会同时冤枉两边：对慢的那台太严，对快的那台太松。
- **基线取样本最大值，不取平均。** 门禁要拦的是回归，不是描述典型情况。用平均值当基线，意味着有一半的正常运行天生就在基线之上，只能靠余量兜——那余量就不再是"允许多少回归"，而是"填补取样口径的错"。
- **余量固定 20%**，含义是环境波动加上可接受的回归。改余量是产品决策，不该混在校准里顺手做掉。

### 还缺业务样本

§14 要求的是"按真实 CI 历史**与业务样本**校准"。上面的流程解决前半句。后半句要等有真实业务文档之后，把基准负载换成或补上取自真实文档的分布（段落长度、图片密度、表格规模）——现在这份 5 万字/300 段/50 图/20 表的负载是构造出来的，它的形状未必是用户文档的形状。

## 各条指标的口径

§14.2 的节点数上限落在事务入口，因此在每一次按键的路径上。它的常态开销与写入量成正比而不是与文档大小成正比：会话维护一个只增的保守上界，只有上界触到 20000 时才做一次全文遍历并把上界收回真实值。打字因此是 O(1)，全文遍历只发生在装载时和文档确实逼近上限时。`keypressToRedrawP95Ms` 覆盖这条路径。

字数统计（§4.4）当前是**全量重算 + 按内容变更缓存**，没有做增量维护。理由是实测：5 万字基准文档一次全量统计约 18ms（含 `Intl.Segmenter` 的字素簇分段），与工具栏状态计算同一量级，而缓存让它每次内容变更最多发生一次。增量维护要按 step 的插入/删除文本加减，代价是字素簇会在删除边界上被拆开数错——为一个已经在预算内的路径引入会悄悄算错的实现，不划算。`wordCountMs` 就是为了让这个判断可被推翻：它一旦逼近预算，再换增量。

当前没有自定义 NodeView；因此不存在可延迟挂载的 NodeView 工作。新增 NodeView 时，必须在同一变更中采用可见区域/按需挂载，并重新评估相应基线。

Markdown 导出（§4.3）走的是与 `getHTML()` 同一条纯 JS 路径，没有单独的基准项：它的复杂度与 HTML 渲染同阶，而 HTML 渲染已在内存增量那一项里被覆盖。导入侧带 CommonMark 解析器，但它在可选包里、不在编辑路径上，不进本门禁。
