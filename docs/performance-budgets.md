# 性能基准与 CI 门禁

运行 `pnpm bench` 会构造固定负载：5 万个 Unicode 字符、300 个顶层段落、50 张图片、20 个 3×3 表格和 4 层列表。输出以下五项指标：

- 编辑器完成装载并可供订阅的耗时。
- 选区格式化后的状态更新 p95。
- 解析 1 万字外部 HTML 粘贴的耗时。
- 工具栏状态计算耗时。
- 字数统计耗时（内容变更后的第一次读取）。
- 装载、读取 JSON 和渲染 HTML 的堆内存增量。

`scripts/benchmark.ts` 中的数值是初始 CI 阈值：代码以 20% 余量从基准值计算上限。它们不是已采集的 Node 22 CI 历史基线。GitHub Actions 的 `Quality` 检查会运行该命令，任何指标超过上限都会失败并显示具体指标。

基准通过 jsdom 挂载 `EditorView`，因此可覆盖装载、事务和 DOM 更新路径，但不代表真实浏览器的布局、绘制或 GPU 性能。要校准阈值时，先在 Node 22 CI 连续记录至少三次结果及运行环境，再在同一个 PR 中更新脚本常量和本文件。

§14.2 的节点数上限落在事务入口，因此在每一次按键的路径上。它的常态开销与写入量成正比而不是与文档大小成正比：会话维护一个只增的保守上界，只有上界触到 20000 时才做一次全文遍历并把上界收回真实值。打字因此是 O(1)，全文遍历只发生在装载时和文档确实逼近上限时。`keypressToRedrawP95Ms` 覆盖这条路径。

字数统计（§4.4）当前是**全量重算 + 按内容变更缓存**，没有做增量维护。理由是实测：5 万字基准文档一次全量统计约 18ms（含 `Intl.Segmenter` 的字素簇分段），与工具栏状态计算同一量级，而缓存让它每次内容变更最多发生一次。增量维护要按 step 的插入/删除文本加减，代价是字素簇会在删除边界上被拆开数错——为一个已经在预算内的路径引入会悄悄算错的实现，不划算。`wordCountMs` 就是为了让这个判断可被推翻：它一旦逼近预算，再换增量。

当前没有自定义 NodeView；因此不存在可延迟挂载的 NodeView 工作。新增 NodeView 时，必须在同一变更中采用可见区域/按需挂载，并重新评估相应基线。
